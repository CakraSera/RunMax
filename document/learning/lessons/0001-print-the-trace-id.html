Lesson 0001 · Tracing debug

Print the trace id

Tracing debug is the same move as console.log: print a value you can search for. flush() is not that value.

The trap

Langfuse does not send a trace the moment the agent finishes. It queues work and ships it in the background so the app stays fast. That is official behaviour, not a bug. (Core Concepts, Queuing / batching.)

A short script like pnpm runner:dev can exit while the queue is still in memory. flush() / close() exist so the process waits for a send attempt. An empty queue still “succeeds.” You get no error and no row in the UI.

console.log("ran") proves a line executed. await langfuse.flush() proves the exporter woke up. It does not prove Langfuse stored a trace.

The three-line debug

After agent.generate() (or runBuildThisWeek), print the id the run claims, then flush, then search that id. 

const result = await agent.generate({ prompt, trace: { name: "BuildThisWeek" } });
console.log("traceId", result.trace?.traceId);
await langfuse.close(); // flush + stop, for short scripts

In this repo the workflow already names the run BuildThisWeek. The missing piece is almost always the printed id.

  1. Run pnpm --filter @runmax/agent runner:dev with that log line (or log result.trace inside runBuildThisWeek).
  2. Copy the traceId from the terminal.
  3. Langfuse UI → Traces → last 24h, no filters → search that id. Or GET /api/public/traces/{id} with your project keys.

Three outcomes, three different bugs:

You seeMeans
No traceId printed The observer never started. Wiring, not Langfuse.
Id printed, API 404 / UI empty after a minute Created locally, not ingested (export filter, keys, or process exit).
Id in API, missing in UI Ingest worked. Your view is filtered (environment, time range, type).

Check yourself

1. generate() finished, flush() returned, UI empty. First move?

2. Why can flush succeed with no Langfuse row?
